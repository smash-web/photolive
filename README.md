# PhotoLive — каркас проекта

Веб-приложение: админ загружает пары фото+видео, клиент видит галерею
(по регистрации или по прямой ссылке), при наведении на фото играет
привязанное видео. Отдельно — сканер: наводишь камеру телефона на
**распечатанное** фото, приложение узнаёт его по компьютерному зрению
(без QR) и запускает видео.

## Архитектура

```
                     ┌────────────────────┐
                     │      Supabase       │
                     │  Auth / Postgres /  │
                     │      Storage         │
                     └─────────┬────────────┘
                               │ service role key
                     ┌─────────▼────────────┐
   React (web/)  ───▶│  FastAPI (recognition-│
   Admin / Gallery   │  service/) — вся      │
   / Scan            │  бизнес-логика + CV   │
                     └────────────────────────┘
```

- **Supabase**: регистрация/вход клиентов и админа, база данных (таблицы
  `profiles`, `pairs`), хранение файлов (buckets `photos`, `videos`).
- **FastAPI-сервис**: единственная точка, где лежит `service_role` ключ
  (никогда не должен попасть во фронтенд). Обрабатывает загрузку,
  выдачу галереи (и по логину, и по токен-ссылке), и распознавание.
- **Почему Python, а не Node для бэкенда**: распознавание фото с камеры
  требует OpenCV (ORB features + RANSAC-проверка геометрии) — в Python
  это "из коробки", в Node — не полноценно.

## Как работает распознавание (не QR)

1. При загрузке фото сервер считает ORB-дескрипторы (устойчивые
   локальные особенности изображения — углы, текстуры) и хранит их
   в базе рядом с фото.
2. Когда клиент наводит камеру, каждые ~1.5 сек кадр отправляется на
   `/recognize`. Сервер сравнивает дескрипторы кадра с дескрипторами
   **только тех фото, что принадлежат этому клиенту** (это и быстрее,
   и безопаснее — поиск не идёт по всей базе).
3. Совпадение подтверждается через гомографию (RANSAC) — проверяется,
   что найденные точки совпадения геометрически согласованы, а не
   просто "похожи". Это защищает от ложных срабатываний и работает
   при съёмке под углом/при плохом освещении — то, с чем не справился
   бы обычный perceptual hash.

Если каталог фото на клиента вырастет до сотен — стоит добавить FAISS
для быстрого поиска по дескрипторам, но пока поиск идёт линейно, т.к.
он итак ограничен фото одного клиента.

## Запуск

Два варианта: локально на своём компьютере (нужно ставить Node.js и
Python), или полностью через браузер, без установки чего-либо на
свой компьютер (хостинги сами собирают код). Ниже — оба.

### Вариант А: без установки на свой компьютер (через хостинги)

1. **Supabase** — как описано ниже в шаге 1.
2. **GitHub**: создать аккаунт на github.com, создать новый репозиторий
   (New repository), затем на странице репозитория нажать
   "uploading an existing file" и перетащить туда всю папку
   `photolive-app` (или её содержимое) — без git и терминала.
3. **Backend на Render.com** (или Railway.app): New → Web Service →
   подключить репозиторий → Root Directory: `recognition-service` →
   Build Command: `pip install -r requirements.txt` → Start Command:
   `uvicorn main:app --host 0.0.0.0 --port $PORT` → в Environment
   Variables добавить `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`,
   `SUPABASE_JWT_SECRET` (значения из Supabase, шаг 5 ниже). После
   деплоя скопировать выданный URL (например
   `https://photolive-api.onrender.com`).
4. **Frontend на Vercel.com**: New Project → импортировать тот же
   репозиторий → Root Directory: `web` → Framework: Vite (определится
   само) → Environment Variables: `VITE_SUPABASE_URL`,
   `VITE_SUPABASE_ANON_KEY`, `VITE_API_BASE` (= URL backend'а с шага 3).
   Deploy — получишь публичный адрес сайта.

Всё, дальше можно открывать сайт с телефона по этой ссылке — ничего
локально ставить не пришлось.

### Вариант Б: локально на своём компьютере
1. Создать проект на supabase.com.
2. Выполнить `supabase/schema.sql` в SQL Editor.
3. Storage → создать buckets `photos` и `videos` (private).
4. Создать первого админа: зарегистрировать пользователя через
   Supabase Auth UI, затем вручную в таблице `profiles` добавить строку
   с его `auth_user_id` и `role = 'admin'`.
5. Взять из Settings → API: `URL`, `anon key`, `service_role key`,
   `JWT secret`.

### 2. Backend
```bash
cd recognition-service
pip install -r requirements.txt
export SUPABASE_URL=...
export SUPABASE_SERVICE_ROLE_KEY=...
export SUPABASE_JWT_SECRET=...
uvicorn main:app --reload --port 8000
```

### 3. Frontend
```bash
cd web
npm install
# создать .env:
# VITE_SUPABASE_URL=...
# VITE_SUPABASE_ANON_KEY=...
# VITE_API_BASE=http://localhost:8000
npm run dev
```

## AR-режим (`/scan/ar`, `/scan/ar/:token`)

Это настоящий AR: видео "приклеено" к найденному фото и двигается
вместе с камерой, а не просто разворачивается на весь экран после
паузы (это делает `/scan` — оставлен как более простой и надёжный
запасной вариант).

Работает иначе, чем `/scan`: распознавание и отслеживание идут
**прямо в браузере** через OpenCV.js (WASM), а не через сервер —
эндпоинт `/gallery/features` один раз отдаёт браузеру "сырые" ORB-
дескрипторы фото клиента, и дальше сервер вообще не участвует в
процессе наведения камеры.

**Это прототип, не протестированный на реальном устройстве** — у
меня в этой среде нет браузера с камерой, чтобы прогнать код живьём.
Скорее всего понадобится:
- Открывать `/scan/ar` строго по HTTPS (или на localhost) — иначе
  браузер не даст доступ к камере.
- Подстроить пороги в `ArScanPage.jsx` (`MIN_GOOD_MATCHES`,
  `MIN_INLIERS`, `DETECT_INTERVAL_MS`) под реальные условия —
  глянцевая печать, освещение, дистанция до фото сильно влияют на
  число распознанных точек.
- Проверить производительность на слабых телефонах — ORB-детекция
  в WASM в браузере ощутимо тяжелее, чем на сервере; если будет
  тормозить, можно снизить частоту `detectTick` (сейчас ~5-6 раз/сек)
  или уменьшить размер кадра перед анализом.

## Что доделать перед продакшеном

- HTTPS обязателен для доступа к камере (`getUserMedia`) на реальных
  устройствах — на localhost исключение сделано браузерами.
- Ограничить CORS в `main.py` конкретным доменом фронтенда.
- Добавить rate-limiting на `/recognize`, чтобы не заспамить сервер
  кадрами с камеры.
- Сжатие/ресайз видео при загрузке (иначе будут тяжёлые галереи).
- Продумать срок жизни access_token (сейчас бессрочный) — можно
  добавить `expires_at` в `profiles`.
